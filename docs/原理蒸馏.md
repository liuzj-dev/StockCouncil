# 原理蒸馏：从 AlphaCouncil 到 StockCouncil

> 本文回答一个问题：**原项目「全自动股票分析」到底靠什么在工作？** 把它的机制拆到"可复现的原理"层级，
> 再看本平台（StockCouncil）在每一层做了什么升级。

---

## 一、原项目是什么

| 项目 | 说明 |
|---|---|
| 形态 | 单页 React（Vite）+ Vercel Serverless Functions |
| 前端 | `App.tsx` / `components/AgentCard.tsx` / `constants.ts`（角色定义）/ `lib/storage.ts`（localStorage） |
| 后端 | `api/ai/{gemini,deepseek,qwen}.js`（模型代理）、`api/stock/[symbol].js`（行情代理） |
| 数据来源 | **聚合数据 Juhe**「沪深股票-基本数据接口」（付费） |
| 模型 | Gemini 2.5 Flash、DeepSeek-Chat/Reasoner、Qwen-Plus/Turbo |
| 存储 | 浏览器 localStorage |
| 核心玩法 | 10 个 LLM 角色组成「投资委员会」，四阶段流水线给出一份最终指令 |

一句话概括：**它把"一个人问一次大模型"升级成"10 个角色按组织流程开会"**。

---

## 二、核心机制拆解（8 条可复现原理）

### 原理 1 · 角色分工 = 认知多样性（Role Diversity）

单一模型只有一个"视角先验"，容易被一种叙事带偏。原项目用 10 个角色强制注入不同先验：

```text
第一阶段（5 人，专业分析师）  宏观政策 / 行业轮动 / 技术面 / 资金流 / 基本面估值
第二阶段（2 人，总监整合）    基本面研究总监 / 市场动能总监
第三阶段（2 人，风险控制）    系统性风险总监 / 组合风险总监
第四阶段（1 人，最高决策）    投资决策总经理（GM）
```

每个角色有独立的 `systemPrompt`（人格 + 输出格式）与 `temperature`（0.15 冷静技术派 → 0.45 激进拍板者）。
**分歧本身就是信息**——一致的极端才是信号。

### 原理 2 · 信息流拓扑 = 逐层收敛的漏斗（Information Funnel）

这是整个系统最关键的设计：**不是所有人看到同样的材料，而是按"该看什么"分级投喂**。

```text
Stage 1  5 位分析师：只看【事实底稿】，彼此隔离（并行，互不污染，保证独立性）
Stage 2  基本面总监 ← 宏观 + 行业 + 估值       ┐
         动能总监   ← 技术 + 资金             ┘ 按"脉络"两两整合
Stage 3  系统性风险 ← 宏观 + 两位总监          ┐
         组合风险   ← 技术 + 两位总监          ┘ 审阅前序，找风险点
Stage 4  GM ← 全部 9 份报告，给出唯一指令
```

原理：**注意力路由**。下游只吸收与自己职责相关的上游结论，避免"信息过载导致的平均化平庸"，
同时让每条脉络（基本面线 / 动能线）在 Stage 2 各自收敛成更有分量的判断。

### 原理 3 · 并行 + 串行混合调度

- **Stage 内部并行**（`Promise.all`）：5 个分析师同时跑，墙钟时间 ≈ 最慢的一个。
- **Stage 之间串行**：下游依赖上游产出，必须等待。

这是"延迟"与"依赖"的经典权衡：**同一层能并行就并行，跨层必须串行**。

### 原理 4 · 立场结构化 = 让"观点"可计算

自然语言无法做一致性统计。原项目用 Markdown 关键词收敛立场：

```text
🟢 买入 / 🟡 观望 / 🔴 卖出     （GM 的最终指令，三选一）
多空一致性判断：强多 / 偏多 / 中性 / 偏空 / 强空
动能 + 技术 + 资金 三者同向偏多 → 「强势多头结构」
系统性风险总监「一票否决 = 是」 → 强制降仓
```

原理：**把开放式生成压成离散标签 + 分数**，才能做后续的聚合与风控规则。
（原版靠 `text.includes('🟢 买入')` 判定——本平台把这个弱点补掉了，见原理 5。）

### 原理 5 · 规则化聚合 = 反幻觉的第二道闸门

只让一个 LLM（GM）拍板，存在"单点幻觉"风险。原项目在 GM 之外写死了一套**聚合规则**：

| 规则 | 触发条件 | 效果 |
|---|---|---|
| 多头一致性强 | ≥ 6/9 角色偏多 | 认定为强多头 |
| 空头一致性强 | ≥ 6/9 角色偏空 | 认定为强空头 |
| 强势多头结构 | 动能 + 技术 + 资金 **三者**同向偏多 | 结构性强势，加仓 |
| 一票否决 | 系统性风险总监否决 | 风险优先，强制降仓 |

原理：**LLM 负责"生成观点"，规则引擎负责"复核观点"**，两条独立轨道互相印证。

### 原理 6 · 实时数据注入 = Grounding（把事实钉进 prompt）

原项目在每次调用前，把行情压成一段「事实底稿」文本，塞进所有角色的 prompt：

```text
【实时行情底稿】
股票：贵州茅台(600519) | 现价 1288.00 | 涨跌 +1.98%
今开 1262.95 昨收 1263.00 最高 1288.00 最低 1261.00
成交量 31556 手 成交额 40.43 亿元 换手率 0.25%
五档盘口：卖1 1288.00 / 10手 …… 买1 1287.00 / 6手
```

原理：模型的"知识"有截止日期且会幻觉，**只有把当日真实数字喂进去，分析才有锚点**。
这是整套系统里"事实"与"观点"的分界线。

### 原理 7 · 模型无关的适配层（Provider Abstraction）

原项目支持 Gemini / DeepSeek / Qwen 三种后端，靠一层薄薄的**统一调用接口**收敛协议差异：

```text
generateAgentResponse(agentConfig, symbol, apiKeys, context, stockData)
   ├─ Gemini  → POST /v1beta/models/{model}:generateContent   （原生协议）
   ├─ DeepSeek→ POST /chat/completions                        （OpenAI 兼容）
   └─ Qwen    → POST /compatible-mode/v1/chat/completions      （OpenAI 兼容）
```

原理：**上游（编排逻辑）只认「(system, user) → text」这个契约**，换模型 = 换一个适配器，不动业务。
本平台把这条原理放大成"端口"概念（见第四节）。

### 原理 8 · 可解释可视化（模型直接吐图表 JSON）

原项目让两个角色在 Markdown 末尾附一个 JSON 代码块供前端作图：

```json
{"chartType":"bar","data":[{"name":"行业A","value":40}, ...]}         // 行业轮动
{"chartType":"radar","data":[{"subject":"估值","A":80,"fullMark":100}, ...]} // 基本面五维
```

原理：**让"结构化副产物"跟着自然语言一起产出**，前端正则提取后渲染，图 + 文相互印证。

## 三、原项目的工程短板（本平台要修的）

| # | 短板 | 后果 |
|---|---|---|
| 1 | 依赖**聚合数据 Juhe 付费接口** | 需付费、易停服，个人难以长期运行 |
| 2 | API Key 从浏览器经 serverless 转发 | 暴露面大，且**无降级**：某模型挂了整条流程就废 |
| 3 | 失败处理 = `try/catch` 返回错误字符串 | 错误串会被当成"分析结论"继续往下传，污染下游 |
| 4 | 靠 `includes('🟢 买入')` 判定立场 | 模型换个措辞（"建议吃货"）就失效 |
| 5 | 只用 localStorage | 换设备就丢；无历史对比、无回放 |
| 6 | 图表 JSON 正则提取，容错差 | 一个多余空格就渲染失败 |
| 7 | 模型名/端口硬编码在角色定义里 | 改配置要改代码 |

## 四、StockCouncil 的升级点（逐条对照）

| 维度 | AlphaCouncil（原版） | StockCouncil（本平台） |
|---|---|---|
| 行情数据 | 聚合数据 Juhe（付费，单一源） | **腾讯 / 新浪 / 东财 三源冗余**，自动切换并记录溯源（免费） |
| 模型端口 | 3 个，硬编码在角色里 | **8 个可插拔端口**：gemini / grok / openai / **chatgpt(预留)** / deepseek / qwen / custom / mock |
| 失败处理 | 返回错误串（污染下游） | **端口级降级链**：主端口失败 → 依次尝试备用端口 → 兜底 Mock，全流程绝不中断 |
| 立场解析 | 关键词 `includes` | **三级解析**：JSON 结构化块 → 关键词 → 中性兜底；并给出 `parseMode` 供审计 |
| 决策复核 | 仅规则阈值 | **GM + 规则引擎双轨**，冲突时显式标注 `engineConflict` |
| 角色-端口绑定 | 改代码 | **运行期可配置**（前端「角色路由」面板），持久化到 `data/config.json` |
| 持久化 | 仅 localStorage | **服务端 JSON 历史记录**（上限 100 条）+ 一键回放 |
| 传输 | 一次性返回（等全部跑完） | **SSE 流式推送**：每个角色跑完即渲染，过程可见 |
| 图表容错 | 正则提取 | 结构化块提取 + 字段兼容（`name/label/sector`、`value/score/pct`） |
| 依赖 | React + Vite + Vercel Functions | **零依赖**：Node 内置模块 + 原生 JS/CSS，`node server/index.mjs` 直接跑 |
| 部署 | 需 Vercel | 本地 / 局域网 / 任意支持 Node≥20 的机器 |

## 五、本平台架构（三层）

```text
┌──────────────────────────────────────────────────────────────────┐
│ 表现层  web/  index.html · styles.css · app.js（原生，零依赖）      │
│         输入 → SSE 实时渲染：行情底稿 / 10 张角色卡 / 决策面板      │
├──────────────────────────────────────────────────────────────────┤
│ 编排层  server/orchestrator.mjs   四阶段流水线（并行池 + 串行阶段） │
│         server/agents.mjs         10 角色人格 + 结构化裁决契约      │
│         server/store.mjs          历史记录持久化                    │
│         server/index.mjs          零依赖 HTTP + SSE 服务            │
├──────────────────────────────────────────────────────────────────┤
│ 端口层  server/providers.mjs      统一适配：gemini 原生 / openai 兼容 / mock
│         server/config.mjs         端口注册表 + 就绪判定 + auto 路由 + 降级链
├──────────────────────────────────────────────────────────────────┤
│ 数据层  server/market.mjs         三源行情 + K线 + 本地派生指标      │
│                                    腾讯 → 新浪 → 东财（失败自动换源）│
└──────────────────────────────────────────────────────────────────┘
```

### 一次分析的完整时序

```text
POST /api/analyze  ───────────────►  SSE 流
  ├─ start                                    前端：切到工作台视图
  ├─ stage_start(0)  ─┐
  │   腾讯/新浪/东财 取现价、五档、K线            │  Stage 0 数据层
  │   本地算 MA/波动率/分位/回撤                 │  （把事实钉死）
  ├─ market          ─┘  ◄── 行情底稿注入后续所有 prompt
  ├─ stage_start(1) → 5 分析师并行（并发池 ≤ N）
  │   每个 agent_start / agent_done 实时推送
  ├─ stage_start(2) → 2 总监（按脉络整合）
  ├─ stage_start(3) → 2 风控（含一票否决）
  ├─ stage_start(4) → GM（读全部 9 份）
  ├─ decision  ◄── GM 指令 + 规则引擎复核 + 一致性/倾向指数
  └─ done      ◄── 落盘历史记录，返回 historyId
```

## 六、端口（Provider）的原理

「端口」= **被统一适配的一个 LLM 端点**。三个属性定义它：

```js
{ id, kind, envKey, baseUrlEnv, baseUrl, defaultModel, models }
//  kind: 'gemini'  → Google 原生协议（支持 googleSearch grounding）
//        'openai'  → OpenAI 兼容协议（Grok / OpenAI / ChatGPT / DeepSeek / Qwen / 自定义 都走这条）
//        'mock'    → 离线演示，不发任何外部请求
```

### 就绪判定（三态）

| 状态 | 条件 | 含义 |
|---|---|---|
| `ready` | 有 Key（且自定义端口还需 BASE_URL） | 可直接调用 |
| `missing-key` | 缺 API Key | 需在 `.env` 配置 |
| `reserved` | `reserved: true` 且缺 BASE_URL/Key | **预留插槽**，配置后自动转 ready |

### 路由与降级

```text
resolveProvider(role)                 决定"首选"端口
   ├─ 角色显式绑定且端口 ready  → 用它
   ├─ 否则按 AUTO_PRIORITY[role] 依次找第一个 ready 的端口
   └─ 全不可用 → mock（offlineDemo）或 mock 兜底

fallbackChain(role, primary)          决定"失败后"的顺序
   primary → AUTO_PRIORITY 其余 → 全局顺序 → mock
```

**每个角色独立走自己的链**：GM 用 OpenAI 挂了不影响技术面用 DeepSeek——这就是"绝不中断整个流程"的实现方式。

### ChatGPT 预留插槽的设计

`chatgpt` 端口 `kind: 'openai'`、`reserved: true`、`baseUrl: ''`。
**同时**配置 `CHATGPT_BASE_URL` + `CHATGPT_API_KEY` 后才变 `ready`。
这样它既能指向官方端点，也能指向 **Azure OpenAI / 企业网关 / 任意 OpenAI 兼容代理**，
是留给用户"以后接入 ChatGPT 系"的插槽——现在不阻塞其它端口运行。

## 七、把"结论"变成"纪律"：聚合引擎在算什么

聚合引擎不产生观点，只**复核**观点。它对 10 份结构化裁决做加权统计：

```text
biasIndex  = Σ(立场权重 × 阶段权重) / Σ(2 × 阶段权重)      // -1 ~ +1 多空倾向
             立场权重：强多+2 偏多+1 中性0 偏空-1 强空-2
             阶段权重：分析师1  总监1.5  风控1  总经理2
avgScore   = Σ(0-100分 × 阶段权重) / Σ阶段权重             // 0-100 看多强度
consistency= 偏多占比 ≥2/3 → 强多 / >50% → 偏多 / 反向同理 → 强空/偏空
strongBull = 技术 & 资金 & 动能总监 三者同时偏多            // 强势多头结构
veto       = 系统性风险总监 一票否决 = 是
engineAction = biasIndex>0.15 且 avgScore≥55 → 买入
               biasIndex<-0.15 且 avgScore≤45 → 卖出
               否则观望；若 veto 则买入降级为观望
conflict   = (GM.action ≠ engineAction)                    // 双轨分歧标记
```

**设计哲学**：LLM 给"判断"，规则给"约束"。规则引擎的结论既可以直接作为最终指令，
也可以只作为对 GM 的**审计对照**——两者不一致时系统会明确标出来，而不是静默选一个。

## 八、可以继续演进的方向

1. **接入真实历史回测**：把 `data/history.json` 的每次指令与次日/5日/20日真实涨跌对齐，统计胜率与盈亏比（把"委员会"变成"可验证的策略"）。
2. **端口级加权投票**：给不同模型端口设可信度权重，而非等权。
3. **多标的横向委员会**：一次分析一篮子股票，让行业轮动角色做真正的横向比较。
4. **成本/延迟看板**：记录每个端口的 token 用量、延迟、失败率，自动调优路由。
5. **对话式追问**：对某个角色的报告追问「你为什么这么判断」。
